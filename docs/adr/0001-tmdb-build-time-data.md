# ADR 0001: Source movie data from TMDB at build time

- **Status:** Accepted
- **Date:** 2026-07-07
- **Amended by:** [ADR 0002](0002-movie-night-rooms.md) — rooms add a free-tier backend; the "no backend" principle now applies to the core solo experience

## Context

All lineups are hand-written in `src/data/movies.ts` (~250 unique movies across 10 lists),
with two companion files keyed by `` `${title}|${year}` ``:

- `src/data/posters.ts` — generated by `scripts/fetch-posters.mjs`, which scrapes each
  film's Wikipedia article for its infobox poster. It works, but needs a hand-maintained
  alias table for titles that don't match article names, a year-matching heuristic to
  dodge wrong articles, an 800ms throttle, and it still misses some films.
- `src/data/cast.ts` — fully hand-curated; every new movie means looking up and typing
  the top-billed cast.

Adding a movie is three manual steps; adding a whole themed list is an evening. There is
no way to refresh a list (say, pull in 2025's releases) short of re-curating it.

A core design principle, stated in the README, constrains any fix: **no backend, no
accounts, no API keys at runtime** — the built site is static and the only runtime
network use is loading poster images. Whatever supplies the data must not ship a secret
in the bundle or add a server.

The app may ship publicly under a real domain, so licensing terms matter.

## Decision

Use the TMDB (The Movie Database) API as the data source, invoked **only at build time**
from a Node script — the same pattern as `fetch-posters.mjs`, which it replaces. The
script serves two modes:

1. **Enrich** the hand-curated lists: resolve each `title|year` via TMDB search, then
   write posters (from `image.tmdb.org`) and top-billed cast (from `/credits`) into the
   existing `posters.ts` / `cast.ts` shape. Blurbs stay hand-written — the editorial
   voice is a feature; TMDB overviews are plot summaries, not taglines.
2. **Generate** lists from a declarative config: a list can be defined as a TMDB query
   (e.g. `discover: genre=horror, vote_count≥1000, sort=vote_average` or
   `top_rated`, capped at N titles) instead of hand-picked entries. Regenerating is a
   script re-run.

The TMDB API key lives in a local/CI environment variable (`TMDB_API_KEY`) and never
appears in the bundle. Poster images are hotlinked from TMDB's CDN, which requires no
key — runtime behavior is unchanged from today's Wikimedia hotlinks.

TMDB's free tier requires attribution ("this product uses the TMDB API but is not
endorsed or certified by TMDB"), so the app gains a small attribution notice.

## Alternatives considered

- **Runtime fetch from the browser.** TMDB supports CORS, so the client could call it
  directly, enabling truly live lists ("trending this week"). Rejected: it ships the API
  key in the bundle, adds loading/error states, and makes a deliberately offline-friendly
  static app depend on a third party at runtime. Revisit only if live/trending lists
  become a wanted feature; that would also reopen the serverless-proxy question.
- **Serverless proxy (e.g. Cloudflare Worker) hiding the key.** Rejected outright — it
  is a backend, which the project explicitly does not want to own.
- **OMDb.** Lookup-by-title only (no discover/browse, so it cannot generate lists) and a
  1,000 calls/day free cap. Strictly less capable than TMDB here.
- **IMDb TSV dumps.** Free and good for "top N by rating" at build time, but no posters
  and no cast-billing convenience; would still need a second source.
- **Status quo (Wikipedia scraping + hand-curated cast).** No key needed, but fragile
  (aliases, misses, throttling), covers posters only, and does nothing for list
  generation or cast.

## Consequences

- Adding a movie becomes one line in `movies.ts` plus a script run; posters and cast
  come along automatically. New themed lists are cheap — either curated or query-defined.
- The alias table, year heuristics, and poster misses of the Wikipedia scraper go away;
  `scripts/fetch-posters.mjs` is deleted.
- `cast.ts` stops being hand-curated (existing entries can be kept or regenerated).
- The runtime contract is untouched: static site, no keys, posters hotlinked from a CDN.
- Generated lists are only as fresh as the last script run. That is acceptable — this is
  a curation app, not a news feed.
- New dependencies to live with: TMDB availability at build time, their CDN at view
  time, and their terms — attribution in the UI, and the free key is licensed for
  **non-commercial** use. If the app is ever monetized, TMDB commercial licensing must
  be revisited (or the poster/data source swapped).
- Query-defined lists trade a little editorial control for freshness; hand-picked lists
  remain first-class, so each list can choose its mode.
